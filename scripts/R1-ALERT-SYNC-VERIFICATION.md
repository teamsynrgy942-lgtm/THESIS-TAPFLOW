# R1 automatic alert synchronization: hardware-free verification

The application does not write test alerts. Browser tests intercept Supabase reads and WebSocket messages; they verify frontend behavior without changing research evidence. A real committed database change is still required to establish delivery from the deployed Supabase project.

## Check the project and access first

1. Start `npm run dev`, sign in with the approved dashboard account, and open `/alerts`.
2. In that tab's Console, run:

   ```js
   await (await import('/scripts/check-r1-session.mjs')).checkR1Session()
   ```

   Confirm the intended project hostname, verified user, and `expectedRecords.allVisibleAndRendered === true` for IDs 1 and 3. Their expected historical statuses are RESOLVED and ACTIVE respectively. This diagnostic returns no token, API key, password, or evidence JSON.
3. Run the executable statements in [r1-alert-sync-review.sql](./r1-alert-sync-review.sql) in the matching project's SQL Editor. They are read-only. Check publication membership and INSERT/UPDATE/DELETE flags, primary/replica identity, table grants, RLS policies, required fields, indexes and trigger definitions. Review restrictive policies as well as permissive policies. SELECT visibility must cover ACTIVE and RESOLVED rows.
4. The optional role/claim block in that file checks reads as the actual browser user inside a read-only transaction and rolls back. Owner access in SQL Editor alone does not establish browser access.

If publication membership or event flags are missing, the review file returns proposed SQL as text. Review and apply only the required publication changes manually. Event flags affect all tables in that publication. No SQL runs automatically, and no RLS policy changes are included.

## Prepare isolated data

Prefer a staging clone of the R1 schema, triggers, policies and account permissions, with the local application's existing environment configured through the project's normal configuration procedure. Do not change production credentials for this test. Testing another project proves that project's delivery, not production delivery.

For the deployed project, an authorized reviewer must approve the test row after inspecting the preflight results. Choose a room from the supported rooms 1–3 that the signed-in account can already read and that has no ACTIVE alert with the R1 code. If no suitable room exists, use staging. Do not resolve, delete, reuse, or edit IDs 1 or 3 to free a uniqueness constraint.

Review every required column, foreign key, check constraint, partial unique index and trigger before adapting the INSERT below. The repository does not contain the complete deployed table definition, so this is a review template, not a universal migration. A trigger might write related rows or send notifications; either use staging or define a restoration procedure for those effects before proceeding. Do not disable working detection triggers to run the test.

Choose a new UUID as `TEST_RUN_UUID` and a permitted `TEST_ROOM_ID`. Record the baseline fields for IDs 1 and 3 from the read-only SQL. Record the current active bell count as `N`. Use an ID generated by the table's existing default, return it as text and save it as `TEST_ALERT_ID`. Do not supply an ID or reset a sequence. Default sequence allocation may leave gaps, including after rollback; do not rewind it during cleanup.

## Observe INSERT and UPDATE delivery

Keep `/alerts` open. Development logs show subscription status/errors, event type, and whether a refresh starts or queues. A WebSocket HTTP 101 or a `SUBSCRIBED` message only proves a connection/join. To establish delivery, observe an INSERT or UPDATE log followed by an authenticated alert refresh and the correct UI change.

The existing optional read-only observer can record delivery separately:

```js
const observation = (await import('/scripts/check-r1-session.mjs')).watchR1Realtime(60000);
// Perform the approved SQL in the SQL Editor while this Promise runs.
await observation;
```

This observer creates one temporary additional channel and removes it after the observation window. It never writes a row. The normal application feed remains the source of the displayed state. An empty observation is inconclusive if no committed event occurred in its window.

After adapting and approving the template, execute each mutation separately in the SQL Editor. Replace every placeholder first. Leave IDs 1 and 3 untouched. The guarded INSERT expects `evidence` to be JSONB; adapt only after reviewing its actual type and any extra required fields.

```sql
-- MANUAL TEST ONLY. Commit this statement before waiting for an event.
insert into public.tapflow_r1_alerts
  (detected_at, room_id, code, status, evidence, resolved_at)
select clock_timestamp(), <TEST_ROOM_ID>, 'R1_MISSING_FLOW_SIGNAL', 'ACTIVE',
       jsonb_build_object('tapflow_sync_test_run', '<TEST_RUN_UUID>',
                          'note', 'Controlled frontend synchronization test'),
       null
where not exists (
  select 1 from public.tapflow_r1_alerts
  where room_id = <TEST_ROOM_ID>
    and code = 'R1_MISSING_FLOW_SIGNAL' and status = 'ACTIVE'
)
and not exists (
  select 1 from public.tapflow_r1_alerts
  where evidence ->> 'tapflow_sync_test_run' = '<TEST_RUN_UUID>'
)
returning id::text, room_id, code, status, detected_at;
```

Require exactly one returned row. If none is returned, stop and investigate; never remove an existing row to retry. A concurrent backend insert can still race this guard; a uniqueness error is a reason to stop, not bypass a constraint. Save the exact returned ID. With default SQL Editor autocommit, the statement commits on success. An INSERT that is later rolled back does not produce the committed Postgres Change needed for this test.

Without refreshing the browser, verify all of the following:

- The new ID appears once, with ACTIVE status and the chosen room.
- The bell count becomes `N + 1` and its list contains one matching entry for the test row's room and detection time.
- A new-alert notification appears once. Repeated reads/events must not duplicate it.
- Development logs contain an INSERT event and a refresh associated with that event. A UI change caused only by the 15-second poll establishes fallback behavior, not Realtime delivery.

Now resolve only the tagged test ID:

```sql
-- MANUAL TEST ONLY. Run as a separate committed statement.
update public.tapflow_r1_alerts
set status = 'RESOLVED', resolved_at = clock_timestamp()
where id::text = '<TEST_ALERT_ID>'
  and id not in (1, 3)
  and room_id = <TEST_ROOM_ID>
  and code = 'R1_MISSING_FLOW_SIGNAL'
  and status = 'ACTIVE'
  and evidence ->> 'tapflow_sync_test_run' = '<TEST_RUN_UUID>'
returning id::text, status, resolved_at;
```

Require exactly one returned row. Without reloading, verify that this same ID remains in history as RESOLVED, has its resolution time, disappears from the active bell list, and changes the count back to `N` if no unrelated real event occurred. Confirm the UPDATE event and refresh logs. Use the database baseline to explain unrelated count changes.

## Verify recovery and polling separately

The regression tests cover a joined channel that silently misses changes, unavailable channels, reconnect, focus/visibility/online recovery, pending-read invalidation, duplicate events, route navigation and cleanup. Run the tests listed in the final engineering report; their intercepted traffic is not proof of deployed event delivery.

For a manual fallback check, use the tagged test ID in staging or an approved isolated production test. In DevTools Network request blocking, block only the project's `/realtime/v1/websocket*` connection, then close the existing socket by briefly switching offline and back online. Keep REST/auth requests unblocked and verify that no replacement Realtime socket is receiving events. Commit the approved test INSERT or UPDATE in the SQL Editor. Keep the app visible: it should reconcile through a successful authenticated read at the next approximately 15-second poll without a browser reload. Read duration and browser timer throttling can extend the observed delay. Confirm a poll-triggered refresh in development logs. Remove the blocking rule afterward and verify subscription recovery and an immediate catch-up read.

While offline, database requests cannot succeed. To test return recovery, commit an isolated test change while the app is disconnected, restore the connection, and confirm the online/rejoin refresh brings it up to date. Switch to another tab and back to check visible/focus catch-up. Navigate within the dashboard and return to `/alerts`; the shared feed must still display current state. Logging out must stop R1 subscription and polling activity. Do not use a manual page refresh as the synchronization mechanism.

## Clean up and preserve evidence

First inspect the exact tagged test row. Save any test audit notes separately from historical research evidence. Review trigger side effects and referencing rows before deletion; do not cascade blindly.

```sql

       evidence ->> 'tapflow_sync_test_run' as test_run
from public.tapflow_r1_alerts
```

Require exactly one returned row, verify the test ID leaves history without a reload, and check the DELETE event/refresh or documented polling fallback. Compare IDs 1 and 3 against their baseline: all recorded fields must be unchanged. Restore any separately approved test side effects with the procedure defined during preflight. Remove DevTools blocking and stop temporary observers. Never delete by code/room alone, bulk-clear the table, or reset the sequence.

Record the project, browser account identifier, test ID/run marker, commit times, received event types, UI/count outcomes, polling-only result, and cleanup result.
